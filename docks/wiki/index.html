Guia prático para criar máquinas multibloco com o Infinity Nexus Multiblock.

  • Minecraft: 26.1.2
  • NeoForge: 26.1.2.124
  • Java: 25
  • Idioma dos exemplos: Português
  • Schema atual: schema_version: 2

Este guia documenta tudo o que o JSON aceita hoje e mostra exemplos completos. O objetivo é que você consiga sair de uma ideia e chegar a uma máquina formável, com inventário, energia, fluidos, GUI, receita, boosters e partes móveis.

Para montar e validar a definição visualmente, abra o Builder de multiblocos. Ele exporta o mesmo JSON descrito neste guia.

#1. Como uma máquina funciona

Uma máquina é a combinação de três partes:

  1. O controller único do mod. O bloco, o block entity e o item são registrados uma única vez como infinity_nexus_multiblock:multiblock_controller. Toda definição usa esse mesmo controller; não existe bloco controller por máquina. Texturas por definição são opcionais no campo top-level textures.
  1. Uma definição JSON. Ela diz qual é o pattern, quais blocos formam a estrutura, quais slots existem, qual GUI usar, quais capabilities existem, quais boosters e partes móveis existem e qual receita processar. O vínculo com o controller é feito pelo componente infinity_nexus_multiblock:multiblock_definition, cujo valor é o id da definição.
  1. Um pattern formado no mundo. O jogador coloca o controller virado para a direção correta e clica nele para montar. Quando todas as células batem, o controller fica formed=true, abre a GUI e passa a processar receitas.

Fluxo resumido:

Startup: registra o controller, o item e o tipo de receita
JSON: schema_version 2 + pattern + slots + capabilities + GUI + recipe opcional
Mundo: controller é colocado com o componente de definição e clicado
Loader: valida o JSON e cria a definição
Estrutura: pattern é validado com rotação
Máquina: inventário, energia, fluidos, GUI, receita, boosters e motions funcionam

Não há mais controller nem recipe_type na definição. O controller compartilhado exibe o nome da definição via MultiblockDefinition#displayName(); a chave de tradução é multiblock.<namespace>.<path> e o fallback é o path formatado, como fabrica_de_voxel_cube -> Fabrica De Voxel Cube. Os campos opcionais textures e model permitem especializar as texturas e o modelo 3D do controller por definição; veja a seção 9.2.

No JEI, a categoria de receita é filtrada pelo componente de definição do controller. A categoria de estrutura ainda usa o controller genérico como catalisador e pode listar todas as estruturas; trate isso como limitação conhecida até o filtro por definição ser implementado.

A categoria de receita do JEI usa o mesmo layout da GUI da máquina para item_slots x/y e elementos slot, fluid_bar, energy_bar, arrow, entity e title; o fundo é textures/gui/jei_base.png. A categoria de estrutura usa um painel próprio.

Na GUI da máquina, clicar na seta ou na barra de progresso abre as receitas daquela definição no JEI. Na categoria JEI, a transferência move ingredientes de item para slots input compatíveis; fluidos são inseridos manualmente.

#2. Arquivos, pasta e ID

#2.1 Definição de multibloco

data/<namespace>/multiblock/<arquivo>.json

O campo id precisa ser exatamente <namespace>:<arquivo>.

Exemplo:

data/minhamod/multiblock/fornalha.json

"id": "minhamod:fornalha"

Se o id não bater com o caminho, a definição é rejeitada com:

Definition id ... does not match file id ...

#2.2 Receita

data/<namespace>/recipe/<arquivo>.json

Toda receita de máquina usa "type": "infinity_nexus_multiblock:multiblock" e declara "definition": "<namespace>:<path>". Receitas do controller são geradas pelo mod em data/<namespace>/recipe/controller/<path>.json; veja a seção 9.

#2.3 Datapack

meu_datapack/
  pack.mcmeta
  data/
    minhamod/
      multiblock/
        fornalha.json
      recipe/
        ferro.json

Exemplo de pack.mcmeta para 26.1.2:

{
  "pack": {
    "description": "Minhas máquinas",
    "min_format": [101, 1],
    "max_format": 101
  }
}

Depois de colocar o datapack em world/datapacks, use /reload ou reinicie o servidor.

Datapacks e KubeJS podem adicionar ou sobrescrever definições e receitas. O controller é único e já registrado pelo mod, então qualquer namespace pode usar a mesma estrutura. A receita shaped opcional do controller é gerada a partir do JSON empacotado no jar do mod ou de kubejs/data.

#3.2 Campos de herança

Esses campos são processados antes do schema normal:

CampoObrigatórioTipoPadrãoRegras
extendsnãoidentifier—ID do pai. Não use junto com family.
familynãoidentifier—Alias de extends. Não use junto com extends.
overridesnãoobjeto—Aplicado depois dos campos do filho; vence em caso de conflito.
templatenãobooleanofalseSe true, o arquivo não é registrado como máquina.

Regras:

  • extends e family são a mesma coisa; use apenas um.
  • O pai é resolvido recursivamente.
  • Objetos são mesclados recursivamente.
  • Listas substituem a lista inteira.
  • overrides não pode definir extends, family, overrides ou template.
  • Um template com template: true é sempre ignorado como máquina, mesmo tendo pattern.
  • Um arquivo sem pattern é tratado como template quando é referenciado por outro. Se não for referenciado, é erro de definição.

#3.3 Exemplo mínimo

{
  "schema_version": 2,
  "id": "minhamod:minha_maquina",
  "type": "storage",
  "inventory_rows": 3,
  "pattern": {
    "anchor": "C",
    "layers": [
      [
        "III",
        "III",
        "III"
      ],
      [
        "III",
        "III",
        "ICI"
      ],
      [
        "III",
        "III",
        "III"
      ]
    ],
    "matchers": {
      "I": "minecraft:iron_block"
    }
  }
}

Esse JSON já carrega como definição em qualquer namespace. O item controller recebe o componente de definição com minhamod:minha_maquina; ao colocar o bloco, o block entity usa esse ID. Não é necessário criar bloco por máquina; texturas por definição são opcionais via textures.

#3.4 Migrar do schema 1

  1. Troque "schema_version": 1 por "schema_version": 2.
  2. Remova o objeto controller; o bloco e o block entity agora são compartilhados. Se quiser texturas por máquina, use o novo campo top-level textures.
  3. Remova recipe_type da definição; toda receita de máquina usa infinity_nexus_multiblock:multiblock.
  4. Em cada receita, troque o tipo antigo por "type": "infinity_nexus_multiblock:multiblock" e adicione "definition": "<id da definição>".
  5. Mantenha o campo top-level recipe apenas se quiser gerar a receita shaped do controller.
  6. Gere o controller com /inmb give <id> ou pela aba criativa e rode /reload.

#4. Pattern

#4.1 Regras

  • layers é uma lista de camadas, da base para o topo.
  • Cada camada é uma lista de linhas.
  • Todas as camadas precisam ter a mesma quantidade de linhas.
  • Todas as linhas precisam ter a mesma largura.
  • Espaços (" ") são ignorados como células, mas continuam contando para a largura.
  • anchor é opcional e usa C por padrão.
  • Deve existir exatamente um símbolo de âncora.
  • Cada símbolo usado precisa ter um matcher, exceto a âncora e a Key de upgrade (seção 13).
  • A célula da âncora é o controller. Ela não entra na lista de membros e não é testada pelo matcher.
  • O matcher da âncora é opcional e, se existir, é ignorado.
  • A orientação canônica é com o controller virado para SOUTH.
  • Ao validar, montar ou pré-visualizar com o controller em outra direção, posições e states direcionais são rotacionados.

#4.2 Ordem das linhas e colunas

Na orientação canônica (SOUTH):

  • a camada 0 é a mais baixa;
  • a linha 0 fica no norte;
  • linhas seguintes avançam para o sul;
  • a coluna 0 fica no oeste;
  • colunas seguintes avançam para o leste;
  • a âncora C é a posição do controller.

Exemplo de uma camada 3x3:

[
  "III",
  "I I",
  "III"
]

A linha do meio tem um espaço no centro. O espaço não é uma célula, mas a linha continua com largura 3.

#4.3 Rotação

FACING do controllerRotação aplicada
SOUTHnenhuma
NORTH180 graus
EAST90 graus anti-horário
WEST90 graus horário

O JSON sempre descreve a máquina olhando para SOUTH. Se você escrever facing: "north" em um matcher, esse valor será rotacionado junto com a estrutura quando o controller estiver em outra direção.

#4.4 Exemplo de pattern 3x3x3

"pattern": {
  "anchor": "C",
  "layers": [
    [
      "III",
      "III",
      "III"
    ],
    [
      "III",

O controller fica na face sul da camada do meio. O resto do cubo é minecraft:iron_block.

#4.5 Tamanho

O loader não impõe um limite de tamanho para o pattern. O limite configurável em export.pattern_scan_limit (padrão 256, máximo 40960 blocos) vale para a exportação no criativo, não para a definição.

#5. Matchers

pattern.matchers é um objeto cujo nome da chave é um único caractere e cujo valor pode ser:

  1. uma string com ID de bloco;
  2. uma string com tag de bloco, começando com #;
  3. um objeto com block ou tag e, opcionalmente, state.

#5.1 String de bloco

"matchers": {
  "I": "minecraft:iron_block"
}

O bloco precisa existir no registro.

#5.2 String de tag

"matchers": {
  "I": "#c:storage_blocks/iron"
}

O # é obrigatório nesse formato. A tag é resolvida no registro de blocos.

#5.3 Objeto de matcher

CampoObrigatórioTipoRegras
blockum dos doisstringID de bloco. Não use junto com tag.
tagum dos doisstringID de tag. Pode ter # ou não. Não use junto com block.
statenãoobjetoMapa de propriedade para valor, ambos strings. Funciona com block ou tag.

Exatamente um entre block e tag precisa existir.

Exemplo com bloco e state:

"matchers": {
  "S": {
    "block": "minecraft:oak_stairs",
    "state": {
      "facing": "north",
      "half": "bottom",
      "shape": "straight",
      "waterlogged": "false"
    }
  }
}

Exemplo com tag:

"matchers": {
  "S": {
    "tag": "#minecraft:stairs"
  }
}

Exemplo com tag e state:

"matchers": {
  "S": {
    "tag": "#minecraft:stairs",
    "state": {
      "facing": "south"
    }
  }
}

Com tag + state, o bloco precisa pertencer à tag e ter as propriedades informadas; membros da tag que não têm essas propriedades são ignorados no match.

#5.4 Como o state funciona

  • Apenas as propriedades listadas em state são verificadas.
  • Propriedades omitidas são ignoradas.
  • Um objeto sem state aceita qualquer state do bloco (ou de qualquer membro da tag).
  • Um objeto com state aceita qualquer combinação que bata com as propriedades informadas.
  • Com tag, cada membro é avaliado individualmente: o bloco precisa estar na tag e ter todas as propriedades informadas.
  • O nome da propriedade e o valor precisam existir no bloco. Em um matcher de tag, membros sem a propriedade ou sem o valor válido não casam.
  • Valores são strings: "true", "false", "north", "1", etc.
  • O state é relativo à orientação canônica SOUTH e é rotacionado junto com a estrutura.

Exemplo de matcher parcial para escada:

"matchers": {
  "S": {
    "block": "minecraft:oak_stairs",
    "state": {
      "facing": "south",
      "half": "bottom"
    }
  }
}

Esse matcher aceita a escada virada para sul e na metade de baixo, independentemente de shape ou waterlogged.

#5.5 O que não existe

  • NBT;
  • listas de alternativas (any);
  • matchers opcionais;
  • expressões ou lógica.

Se precisar de alternativas, use uma tag de bloco.

#6. Slots de item

#6.1 Tamanho do inventário

  • Se item_slots tem entradas, o inventário tem exatamente a quantidade de entradas.
  • Se item_slots está vazio ou ausente, o inventário tem inventory_rows * 9 slots.
  • inventory_rows é validado mesmo quando ignorado, então use de 1 a 6.

Exemplos:

ConfiguraçãoTamanho
sem item_slots, inventory_rows: 327
sem item_slots, inventory_rows: 654
4 entradas em item_slots4

#6.2 Campos de item_slots[]

CampoObrigatórioTipoPadrãoRegras
idsimstring—Único e não vazio.
rolesimstring—input, output, fuel, upgrade, component, storage ou fluid.
filternãostringsem filtroID de item ou tag com #.
limitnãointeiro64De 1 a 64. O limite efetivo também considera o tamanho máximo do stack.
facesnãoobjetopadrão do roleinsert e/ou extract, cada um com uma lista de direções.
xnãointeiroausentePosição horizontal na GUI customizada. Precisa de y. Não pode ser negativo.
ynãointeiroausentePosição vertical na GUI customizada. Precisa de x. Não pode ser negativo.

faces:

"faces": {
  "insert": ["north", "south"],
  "extract": []
}
  • insert: faces que podem inserir no slot.
  • extract: faces que podem extrair do slot.
  • Se um dos campos for omitido, vale o padrão do role.
  • Lista vazia desativa a operação.
  • Direções: north, south, east, west, up, down.

#6.3 Faces padrão por role

RoleInsere porExtrai porUso atual
inputtodasnenhumaParticipa do matching de receita.
outputnenhumatodasRecebe o resultado da receita.
fueltodasnenhumaSem comportamento de receita embutido.
upgradetodasnenhumaSem comportamento de receita embutido.
componenttodasnenhumaSem comportamento de receita embutido.
storagetodastodasArmazenamento/automação.
fluidnenhumanenhumaSlot manual: drena o container inserido para o tanque selecionado e enche o container retirado a partir dele.

Apenas input e output têm comportamento automático no processamento de receitas. Os outros roles são úteis para automação, filtros, limites e GUIs; outros mods podem acessá-los pelo inventário.

O role fluid tem comportamento manual: ao inserir um container com fluido ele é drenado para o tanque selecionado; ao retirar um container vazio, ele é preenchido a partir do tanque. O pino azul no slot, exibido quando há mais de um tanque, alterna o tanque usado. Sem faces de automação, o slot não participa de inserção/extração por hopper.

#6.4 Filtro e limite

  • filter aceita ID de item (minecraft:iron_ingot) ou tag (#c:ingots/iron).
  • O filtro vale para o jogador e para automação.
  • O limite vale para o slot e também para o resultado.
  • O jogador pode retirar de qualquer slot visível, mesmo que a face não permita extração por automação.

#6.5 Faces e rotação

As faces de item_slots são direções do mundo. Elas não são rotacionadas junto com o FACING do controller.

Exemplo: "insert": ["north"] continua significando norte do mundo, mesmo que a máquina esteja virada para leste. Para evitar confusão, use faces amplas ou documente a orientação da sua máquina.

#6.6 Slots e GUI

Há dois jeitos de posicionar slots na GUI customizada:

Formato atual: item_slots[] com x/y.

"item_slots": [
  {
    "id": "input_0",
    "role": "input",
    "x": 44,
    "y": 17
  },
  {
    "id": "output_0",
    "role": "output",
    "x": 116,
    "y": 26
  }
]
  • Slots com x/y aparecem na GUI.
  • Slots sem x/y ficam ocultos, mas continuam existindo para automação e receitas.
  • Todos os slots visíveis precisam caber em gui.width/gui.height.

Formato antigo: elementos slot dentro de gui.elements.

{
  "type": "slot",
  "slot": "input_0",
  "x": 44,
  "y": 17
}
  • O slot precisa existir em item_slots[].
  • Cada slot pode aparecer uma vez.
  • Não misture elementos slot com x/y em item_slots[].
  • O tamanho do slot é fixo em 18x18; width/height do elemento são ignorados.

No layout padrão (sem gui.elements), slots com x/y que caibam em 176x166 são respeitados; os demais são distribuídos automaticamente. A grade usa 9 colunas, ou 8 quando há barras de energia/fluido ou barra de progresso.

  }
]

#7. Energia e fluidos

capabilities é opcional e fica no nível raiz. item_slots não fica dentro de capabilities.

#7.1 Energia

"capabilities": {
  "energy": {
    "id": "energy",
    "capacity": 100000,
    "max_receive": 1000,
    "max_extract": 0
  }
}
CampoObrigatórioTipoPadrãoRegras

#7.2 Fluidos

"capabilities": {
  "fluids": [
    {
      "id": "water_tank",
      "capacity": 10000,
      "max_receive": 1000,
      "max_extract": 0,
      "filter": "minecraft:water",
      "port": "F"
    }
  ]
}
CampoObrigatórioTipoPadrãoRegras
idsimstring—Único entre os tanques e diferente do energy.id.
capacitysiminteiro—Mínimo 1, em mB.
max_receivenãointeiro0mB aceitos por inserção. 0 desativa.
max_extractnãointeiro0mB liberados por extração. 0 desativa.
filternãostringsem filtroID de fluido ou tag com #.
portnãostringqualquer portaKey do pattern, ID de bloco ou tag que dá acesso ao tanque.

O port é opcional. Quando definido, o tanque só é exposto nos blocos de fluido que casarem com esse seletor; a key precisa existir no pattern e, quando capability_ports.fluid existe, também precisa estar selecionada lá. Tanques sem port continuam acessíveis por qualquer porta de fluido. Isso permite, por exemplo, um tanque de água acessível só pela key F e um de lava só pela key L.

A automação pelas portas respeita max_receive/max_extract e filter do tanque. O slot fluid e a interação manual com balde/container na porta ou na GUI ignoram max_receive e max_extract (limites de automação), mas respeitam capacity e filter. A troca do slot é all-or-nothing por stack: N baldes exigem N*1000 mB livres no tanque.

Na GUI, clique esquerdo na barra de um tanque usa o item que está no cursor (mouse), não o item da hotbar. Com balde/container de fluido, tenta encher o item e depois drenar o item para o tanque, sem respeitar max_receive/max_extract; um balde vazio é consumido e vira um balde cheio (baldes cheios não empilham, então é 1 por clique). Com esponja seca em um tanque de água, esvazia o tanque e consome 1 esponja do cursor, devolvendo esponja molhada no cursor ou no inventário.

#7.3 Portas de capability (capability_ports)

capability_ports é opcional e fica no nível raiz, irmão de capabilities.

"capability_ports": {
  "item": ["I"],
  "energy": ["C"],
  "fluid": ["F", "#minecraft:glass"]
}
CampoObrigatórioTipoPadrãoRegras
itemnãolistatodosBlocos que expõem a capability de item.
energynãolistatodosBlocos que expõem a capability de energia.
fluidnãolistatodosBlocos que expõem as capabilities de fluido.

Cada item da lista aceita:

  • um símbolo de 1 caractere do pattern (C, I, F...);
  • um ID de bloco (namespace:path);
  • uma tag de bloco (#namespace:path).

Regras:

  • As três chaves são independentes. Omitir uma chave expõe aquela capability em todos os blocos formados; lista vazia ([]) não expõe em nenhum.
  • O controller só expõe uma capability se ele próprio for selecionado (pelo símbolo C ou pelo ID do bloco controller).
  • Um símbolo que não existe no pattern falha o carregamento da definição.
  • A whitelist controla apenas as capabilities do multiblock; capabilities nativas de um bloco membro continuam disponíveis.
  • Não há configuração por face: um bloco selecionado expõe a capability em todas as suas faces.
  • item não é uma chave de capabilities: todo multiblock tem inventário (item_slots ou inventory_rows) e expõe item por padrão. Use capability_ports.item para limitar as portas ou [] para não expor item.
  • energy e fluid só têm efeito quando a máquina define capabilities.energy ou pelo menos um tanque em capabilities.fluids. Um tanque somente de fluido é possível com capabilities.fluids e, se quiser esconder o inventário, "capability_ports": {"item": []}. A GUI customizada pode ter só fluid_bar e player_inventory, sem item_slots.

Além de item, energy e fluid, capability_ports aceita uma chave para cada recurso de addon registrado (por exemplo chemical, mana ou aura). O valor usa o mesmo formato de seletores: símbolo do pattern, ID de bloco ou tag. Um kind que não está registrado falha o carregamento da definição.

As portas são recalculadas na próxima validação da estrutura (a cada 20 ticks ou quando um vizinho muda). /reload atualiza a definição e agenda essa revalidação; não é preciso quebrar e montar de novo.

No builder, os campos de capability_ports ficam na etapa Capabilities. Clique nos símbolos do pattern para alternar vários seletores ou digite símbolos, IDs e tags separados por vírgula ou espaço. Campo vazio omite a chave e libera a capability em qualquer bloco; [] não expõe nenhum bloco. As portas energy/fluid ficam desabilitadas enquanto a capability correspondente não existir.

#7.4 Onde as capabilities aparecem

  • Padrão: todos os blocos membros formados e o controller expõem as capabilities configuradas.
  • Com capability_ports: apenas os blocos selecionados para cada capability.
  • Itens: um hopper encostado em qualquer porta de item acessa o mesmo inventário.
  • Energia e fluidos: normalmente expostos só no controller, incluindo C na lista correspondente.
  • Tanques com port: só aparecem nas portas de fluido que casarem com a key/bloco/tag configurada; as demais portas veem apenas os tanques sem port (e os que casarem com elas).
  • Balde/container de fluido: clicar com o item em uma porta de fluido formada move até 1.000 mB entre o item e o tanque (tenta encher o item primeiro e depois drenar o item), ignorando max_receive/max_extract; o balde é consumido/trocado também no criativo. Sem capability_ports.fluid, qualquer bloco membro serve como porta; com capability_ports.fluid definido, só as portas selecionadas transferem e clicar com um container de fluido em um bloco membro que não é porta cancela a abertura da GUI. Shift+clique criativo para exportar continua funcionando.
  • Barra de fluido na GUI: clique esquerdo na barra do tanque com balde/container no cursor para transferir; com esponja seca no cursor e tanque de água, esvazia o tanque e molha a esponja. O balde não pega recursos de addon (mana, chemical etc.) porque esses recursos usam resource_bar, não fluid_bar.
  • O energy.id e os fluids[].id são usados pela GUI para localizar as barras. Eles não mudam as portas.

#7.5 Energia em receitas

Um input de energia usa { "type": "energy", "amount": 1000 }. A maquina precisa ter capabilities.energy; sem armazenamento, a receita nem inicia.

O custo e distribuido ao longo dos ticks. Uma receita com amount: 1000 e time: 100 consome aproximadamente 10 FE por tick. Se a energia acabar, o progresso pausa. Um output de energia e inserido no storage ao completar.

#7.6 Fluidos em receitas

Se a receita tem inputs do tipo fluid, a maquina precisa ter tanques suficientes. Cada ingrediente de fluido procura um tanque que aceite o fluido e tenha a quantidade necessaria. Cada tanque satisfaz no maximo um ingrediente por craft.

#7.7 Reload

/reload atualiza a definição, mas não recria nem reconfigura capabilities de energia/fluidos já existentes. Se você mudar capacity, max_receive, max_extract ou filter, quebre e coloque o controller de novo, ou reinicie o mundo, para criar as capabilities com os novos valores.

#7.8 Recursos de addon

Além de energy e fluids, capabilities aceita uma chave por recurso de addon registrado. O formato interno de cada kind é definido pelo addon:

"capabilities": {
  "aura": {
    "tanks": [
      { "id": "input", "capacity": 100000, "max_receive": 100, "max_extract": 0 }
    ]
  }
},
"capability_ports": {
  "aura": ["A"]
}
  • O base entrega o JSON bruto de capabilities.<kind> para o addon; quem valida os campos é o próprio addon.
  • capability_ports.<kind> aceita os mesmos seletores de item/energy/fluid.
  • Receitas usam o kind como type do ingrediente/output, por exemplo { "type": "aura", "id": "mymod:ignis", "amount": 100 }.
  • A GUI usa resource_bar (um tanque) ou resource_list (grade de recursos).
  • Se o kind não estiver registrado, a definição falha com uma mensagem como Unknown multiblock resource kind 'aura': is the addon installed?.

O contrato completo para criar um addon está em addons.html.

#8. GUI

#8.1 Layout padrão

Sem gui, ou com gui.elements vazio, o layout é automático:

  • slots do inventário em grade automática (9 colunas, ou 8 quando há barras/progresso); posições x/y que caibam em 176x166 são respeitadas;
  • título no topo;
  • uma barra de energia, se existir;
  • uma barra para cada tanque de fluido, se existirem;
  • uma barra para cada tanque de recurso de addon, se existirem;
  • uma barra de progresso à direita, se type=recipe;
  • inventário do jogador abaixo dos slots;
  • largura fixa em 176 e altura calculada para caber tudo (mínimo 166).

Se você definir gui sem elements, ainda pode definir texture, width, height, texture_width e texture_height; o layout continua automático, mas usa esses valores.

#8.2 Layout customizado

Com gui.elements não vazio:

  • item_slots só é obrigatório quando houver elementos slot ou posições x/y; uma GUI somente de fluidos pode omitir slots de item;
  • os slots visíveis são os que têm x/y em item_slots[], ou os elementos slot no formato antigo;
  • slots sem posição ficam ocultos, mas funcionam para automação/receita;
  • não misture x/y em item_slots[] com elementos slot;
  • exatamente um player_inventory é obrigatório;
  • energy_bar.capability precisa ser igual a energy.id;
  • fluid_bar.capability precisa ser igual a um fluids[].id;
  • progress_bar, arrow e entity só são aceitos em type=recipe;
  • slots, player inventory, barras e entity precisam caber em width/height;
  • entity e resource_list precisam de width/height múltiplos de 18 e no mínimo 18;
  • title e text não têm validação de limites; cuidado para não desenhar fora da tela.
  • Em title/text, x/y representam o canto superior esquerdo da linha de texto, não a baseline; a tela compensa 1 px para alinhar o desenho ao referencial do builder. No builder, a prévia compensa mais 2 px no title e 3 px no text para o texto bater visualmente com o jogo, sem alterar o JSON exportado.
  • No builder, novos elementos começam com o layout do spawner: title em 8,4, text em 8,71 (rótulo do inventário), player_inventory em 8,84, energy_bar/fluid_bar/progress_bar em 158/148/138,16 com 8x54, e entity em 82,16 com 54x54.
  • Uma GUI nova no builder já vem com title, text (Inventário) e player_inventory; a marcação do inventário cobre a área interna dos slots, de 8,84 a 167,157, e as barras são retangulares como no jogo.
  • No builder, o rótulo do inventário vem do elemento text; o player_inventory só desenha o próprio text quando não existe um text com conteúdo na posição do rótulo, evitando dois rótulos na prévia.
  • Slots novos começam em 8,16 e avançam 18 px por coluna, com 9 colunas por linha (ou 8 quando há barras de energia/fluido ou barra de progresso) antes de descer para a próxima linha.
  • O builder usa docks/builder/assets/gui/gui.png (176x166) como fundo padrão, slot.png nos slots e seta_fundo.png com seta_overlay.png animado na seta.
  • O upload de um PNG custom no builder usa o tamanho natural da imagem e bloqueia width, height, texture_width e texture_height até clicar em usar padrão.
  • Os elementos da GUI são acordeões; o seletor de tipo mostra uma descrição curta no hover.
  • Na prévia da GUI do rail, passar o mouse aplica zoom de 1.9x centrado na posição do cursor; ao sair, a prévia volta ao tamanho normal.

#8.6 Detalhes por tipo

title e text

  • text é uma chave de tradução ou um texto literal.
  • title vazio usa o nome do bloco.
  • Se não houver nenhum title, a tela desenha o título padrão em 8,6.
  • Não há validação de limites para title/text.

player_inventory

  • Ocupa 162x76 (3 linhas + hotbar).
  • O rótulo é desenhado 11 pixels acima de y.
  • text vazio usa container.inventory.
  • Precisa caber em width/height.

slot

  • slot precisa ser o ID de um item_slots[].
  • O slot é desenhado em x,y com 18x18.
  • width/height, text e capability são ignorados.
  • Cada slot pode aparecer uma vez.

energy_bar

  • capability precisa ser igual ao energy.id.
  • width/height precisam ser positivos.
  • direction define o sentido do preenchimento: up, down, left ou right.
  • color define a cor do preenchimento.
  • Tooltip mostra energia/capacidade em FE.
  • Sem textura, desenha um fundo escuro. Com textura, a textura precisa incluir o fundo.

fluid_bar

  • capability precisa ser igual a um fluids[].id.
  • width/height precisam ser positivos.
  • Sempre preenche de baixo para cima; direction e color são ignorados.
  • Tooltip mostra o fluido e a quantidade.
  • Sem textura, desenha um fundo escuro.

progress_bar

  • Só em type=recipe.
  • width/height precisam ser positivos.
  • direction define o sentido do preenchimento.
  • color define a cor do preenchimento.
  • Com textura, desenha o sprite em u/v como fundo e depois o preenchimento.
  • Sem textura, desenha o fundo escuro.
  • Tooltip mostra a porcentagem do craft atual.

arrow

  • Só em type=recipe.
  • width/height precisam ser positivos.
  • direction define o sentido do recorte.
  • Usa u/v como origem do sprite.
  • Precisa de textura; sem textura, a seta não é desenhada.
  • Não desenha fundo.
  • Tooltip mostra a porcentagem do craft atual.

entity

  • Só em type=recipe.
  • width/height precisam ser múltiplos de 18, no mínimo 18, e caber na GUI.
  • A área é dividida em células de 18x18: com uma entidade, ela ocupa a área inteira; com duas ou mais, cada célula mostra uma entidade em ordem de linha.
  • A capacidade é (width / 18) * (height / 18) entidades por página; quando não couberem, surgem páginas com indicador atual/total.
  • No controller, a roda do mouse sobre o elemento troca de página. No JEI, as páginas alternam automaticamente a cada 2 segundos.
  • No JEI, as entidades vêm dos inputs e outputs do tipo entity da receita exibida, incluindo a quantidade pedida/gerada (count); o elemento não tem campo de ID.
  • No controller, entidades vivas dentro da área do multibloco são exibidas mesmo sem receita ativa; entidades de input/output da receita ativa completam a lista.
  • O fundo é preto e a borda é cinza, no mesmo estilo das barras.
  • O tooltip do JEI identifica entrada/saída, a quantidade e a chance da entidade na página exibida; no controller, mostra o nome e a contagem da entidade.
  • Renderiza no JEI e no controller.
  • Entidades vivas usam o renderer de inventário; entidades não-vivas usam o render state genérico. A escala é ajustada ao tamanho da entidade para caber na célula.

resource_bar

  • capability é o kind do recurso e slot é o ID do tanque retornado pelo addon.
  • width/height precisam ser positivos.
  • Sempre preenche de baixo para cima; direction e color são ignorados.
  • A cor e o nome vêm do addon (color/displayName).
  • chemical_bar é redirecionado para resource_bar.

resource_list

  • capability é o kind do recurso; hoje o builder trata como o caso especial de essentia.
  • width/height precisam ser múltiplos de 18 e no mínimo 18.
  • Desenha uma grade de células de 18x18, como o elemento entity.

booster_button

  • Só é aceito quando upgrades.boosters não está vazio.
  • Padrão 8x8; o builder posiciona no canto superior direito (x=160, y=4 numa GUI 176).
  • Ao clicar, destaca as células de upgrade no mundo por 10s.

Builder: hoje ele converte resource_bar importado para chemical_bar (exceto capability=mana) e trata resource_list como o caso especial de essentia. Para outros kinds, edite o JSON manualmente.

#9. Controller único e receita

#9.1 O controller compartilhado

Todas as definições usam o mesmo bloco, block entity e item:

infinity_nexus_multiblock:multiblock_controller

O vínculo com a definição é o componente:

infinity_nexus_multiblock:multiblock_definition = <namespace>:<path>

A aba criativa gera uma variante do controller para cada definição carregada. Colocar um controller sem esse componente é bloqueado. Ao quebrar, clonar ou dropar o bloco, o componente é preservado.

Para obter uma variante:

/inmb give minhamod:minha_maquina

/inmb list lista as definições e cria links clicáveis para o comando give.

#9.2 Texturas e modelo 3D por definição

Os campos top-level textures e model são opcionais. textures sobrescreve as texturas do modelo compartilhado e model troca o modelo 3D do controller por estado visual. O bloco e o item continuam os mesmos; o cliente re-bakeia o modelo do controller quando a definição ou o estado processing muda.

{
  "textures": {
    "front": "minhamod:block/fornalha_front",
    "side": "minhamod:block/fornalha_side",
    "top": "minhamod:block/fornalha_top",
    "bottom": "minhamod:block/fornalha_top",
    "particle": "minhamod:block/fornalha_front",
    "active": {
      "front": "minhamod:block/fornalha_front_on",
      "side": "minhamod:block/fornalha_side_on"
    }
  },
  "model": {
    "idle": "minhamod:block/fornalha",
    "active": "minhamod:block/fornalha_on",
    "building": "minhamod:block/fornalha_building"
  }
}

Regras de textures:

  • Faces aceitas: all, front, back, left, right, top, bottom, side e particle; left, right e back usam side como fallback.
  • all atende modelos cujas faces usam #all; as faces específicas têm prioridade sobre all.
  • Os valores são identifiers completos, como minecraft:block/stone, e a textura precisa existir em assets/<namespace>/textures/block/... para entrar no atlas de blocos.
  • Faces omitidas usam o modelo/textura padrão do controller.
  • active é opcional e é aplicado enquanto o controller está processando. Faces omitidas em active herdam a textura idle correspondente.
  • building é opcional e é aplicado durante a montagem. Faces omitidas em building herdam active e depois idle.
  • particle vazio usa front; sem front, usa all; sem ambos, usa a partícula padrão do modelo.
  • No builder, o controller custom lista as chaves de textura do próprio JSON do modelo (ex.: #all, #side, #front), não as seis faces padrão. Importar um PNG é apenas visual: não grava em textures nem altera o JSON. A imagem é aplicada a todas as faces que usam aquela chave; se a chave não tiver identifier resolvido, o builder gera um minecraft:... apenas no preview. As imagens ficam salvas por estado (idle, active, building) e voltam ao alternar o preview.
  • Depois do PNG, o botão .mcmeta aplica uma animação só no preview. O builder lê animation.frametime, animation.interpolate e animation.frames (números ou {index, time}), usando o PNG como tira vertical de frames. O .mcmeta não entra no JSON exportado; para o jogo animar, publique o arquivo <texture>.png.mcmeta ao lado do PNG em assets/<namespace>/textures/....
  • Como os demais objetos, textures é mesclado recursivamente por extends, family e overrides; o objeto active é mesclado face a face.
  • Se uma textura não estiver no atlas de blocos do cliente, o controller volta ao modelo padrão e registra um aviso no log; o JSON continua carregando no servidor.
  • A troca idle/active não exige quebrar o bloco; ela acompanha o estado processing do controller.

Regras de model:

  • Valores são identifiers de modelos completos, como minecraft:block/furnace, e o JSON precisa existir em assets/<namespace>/models/....
  • idle é a base. active é usado durante o processamento e building durante a montagem.
  • Fallback: building usa active e depois idle; active usa idle. Sem idle, a definição não troca o modelo.
  • O modelo e o item usam o estado idle; no bloco, a troca acompanha processing/montagem sem quebrar o bloco. O preview do JEI e o ghost preview tambem usam o modelo idle da definicao.
  • textures continua sendo aplicado por cima do modelo escolhido, quando as faces existirem.
  • Se o modelo não puder ser carregado, o controller mantém o modelo padrão do blockstate e registra um aviso no log; o JSON continua carregando no servidor.
  • Limitações: modelos JSON padrão (elements/parent) são o caso garantido; modelos com loaders customizados (OBJ etc.) são best-effort, composites com dependências internas podem não resolver e o modelo precisa caber no espaço de um bloco.
  • Como os demais objetos, model é mesclado recursivamente por extends, family e overrides.

#9.2.1 Shape do controller

O campo top-level shape é opcional e substitui o cubo completo usado na colisão e no contorno de seleção do controller. Cada caixa usa pixels (0–16) no espaço do modelo olhando para o norte e é rotacionada junto com o facing do bloco.

{
  "shape": [
    [4, 0, 4, 12, 16, 12],
    [2, 0, 12, 14, 6, 16]
  ]
}

Cada entrada é [min_x, min_y, min_z, max_x, max_y, max_z].

O botão usar model do builder gera uma caixa AABB por elemento do model.idle, preservando coordenadas fracionárias. Rotações de 90° são exatas; elementos com outras rotações e caixas sem volume são ignorados. Elementos fora de 0–16 são ajustados ao limite e o builder avisa. Como o shape é único, ele não acompanha active/building: use o model.idle como referência de colisão.

Regras de shape:

  • Omitir shape (ou usar uma lista vazia) mantém o cubo completo do controller.
  • As caixas precisam ficar dentro de 0–16 e min não pode ser maior que max.
  • A rotação acompanha o facing: norte 0°, leste 90°, sul 180°, oeste 270°.
  • O shape vale para colisão e para o contorno de seleção; o modelo visual não é alterado.
  • O item no inventário continua sem shape próprio (não é necessário).
  • Como os demais campos, shape é mesclado/substituído por extends, family e overrides.
  • Se o controller ainda não tiver a definição sincronizada no cliente, o shape cai no cubo completo até a sincronização.

#9.3 Como o vínculo é aplicado

  1. O item possui o componente com o id da definição.
  2. Ao colocar o bloco, o componente é copiado para o block entity.
  3. O block entity carrega a definição pelo id e configura inventário, capabilities, GUI e receitas.
  4. Ao clicar com o bloco ainda não formado, a estrutura é validada.
  5. Se o pattern bater, o controller passa a formed=true e processa receitas.

O mesmo controller pode representar qualquer máquina; o bloco é compartilhado e as texturas podem ser especializadas por definição via textures.

#9.6 Montagem incremental e Jade

Clicar no controller não formado (sem agachar) inicia uma montagem incremental que coloca os blocos que faltam. Agachar mostra not_formed; no criativo, agachar com a mão vazia continua exportando o JSON.

  • O trabalho varre as células em assembly.blocks_per_tick (padrão 32, mínimo 1, máximo 4096) por tick.
  • Cada tentativa sem bloco conta para assembly.max_failed_scans_per_tick (padrão 10) e evita travar quando faltam itens.
  • Blocos já corretos não são mexidos; células ocupadas por outro bloco ficam marcadas e são destacadas em vermelho por assembly.blocked_highlight_seconds (padrão 300s).
  • No criativo, os blocos são colocados sem consumir itens.
  • No survival, os itens vêm do inventário do jogador e dos containers adjacentes ao controller; o que foi consumido é descontado no fim do tick.
  • O controller fica com building=true enquanto a montagem roda e a validação normal é pausada.
  • Ao terminar, a estrutura é validada; o jogador recebe uma mensagem de montagem completa, parcial, blocos faltando ou células bloqueadas.

O Jade mostra o estado do controller:

  • Formed/Unformed quando a montagem não está ativa;
  • uma barra ||...== com a porcentagem durante a montagem.

Se a montagem parar no meio (por falta de itens), clicar de novo retoma de onde parou.

  { "type": "item", "ingredient": "minecraft:raw_iron", "count": 2 },

  • Recurso de addon: o type e o kind registrado e os campos vem do codec do addon (id, amount, etc.).

#10.4 outputs

"outputs": [
  {
    "type": "item",
    "id": "minecraft:gold_ingot",
    "count": 2,
    "components": { "minecraft:custom_name": "Ouro" },
    "chance": 0.5
  },
  { "type": "fluid", "id": "minecraft:water", "amount": 500, "chance": 1.0 },
  { "type": "entity", "id": "minecraft:pig", "count": 2, "spawn": "C", "chance": 0.25 },
  { "type": "energy", "amount": 1000, "chance": 1.0 }
]
  • chance e um numero de 0 a 1; default 1.0. Cada output rola separadamente ao completar.
  • Chance 0 nunca gera o resultado, mas os inputs ainda sao consumidos.
  • Itens usam count de 1 a 99 e podem ter components; fluidos usam amount; entidades usam id ou tag (exatamente um), count de 1 a 99 (padrão 1) e spawn opcional (sem seletor, as entidades de saída surgem dentro da área do multibloco); energia vai para o storage do controller.
  • Recurso de addon: o type e o kind registrado; os campos vem do codec de output do addon.
  • O runtime valida todos os outputs antes de iniciar o craft, mesmo os que tem chance menor que 1.

#10.5 Matching e validacao

  • Itens de input sao distribuidos por slots input com busca em profundidade; um slot so pode satisfazer uma entrada por craft.
  • Fluidos seguem a mesma regra nos tanques, respeitando capacidade e filtro.
  • Entidades de input sao procuradas no AABB do multibloco inflado em 1 bloco; com spawn baseado em simbolo/bloco/tag, a busca fica perto da key correspondente.
  • Entidades de output usam o seletor spawn quando informado; sem seletor, o controller procura um piso com dois blocos livres dentro da area do multibloco.
  • Energia de input e consumida aos poucos durante o progresso; sem energia no storage o craft pausa.
  • Antes de completar, o controller simula o consumo dos inputs de fluido e depois encaixa todos os outputs em copias do inventario e dos tanques. Se nao houver espaco para todos, o progresso fica parado.
  • Itens e fluidos gerados sao distribuidos entre slots/tanks disponiveis; tanques usados por inputs podem ser reaproveitados para outputs depois do consumo. Energia gerada fica no storage interno do controller e pode ser extraida pelas portas de energia.

#10.6 Execucao e chance

Ao completar, os inputs sao consumidos e cada output rola sua chance de forma independente. Uma falha de chance nao devolve os inputs. Se o estado da maquina mudou e os outputs nao cabem mais, o craft nao completa e os inputs nao sao consumidos (a energia ja gasta nao volta); o planner revalida o espaco antes de cada avanco.

#10.7 Energia e tempo

Um input energy com amount: 1000 e time: 100 consome cerca de 10 FE por tick. Se a energia acabar, o progresso pausa. Um output energy e adicionado ao storage ao completar e respeita a capacidade maxima.

#10.8 Limites

  • Numero de inputs de item nao pode passar do numero de slots input.
  • Soma dos count de inputs nao pode passar da soma dos limit dos slots.
  • Cada input de item precisa caber em um unico slot, e cada input de fluido precisa caber em um unico tanque.
  • O mesmo vale para outputs e para a quantidade/capacidade dos tanques.
  • amount de energia nao pode passar da capacidade de capabilities.energy.
  • O builder bloqueia exportacao quando qualquer limite e violado; o runtime apenas nao inicia/completa o craft.

#12. Priority, tier e sobreposição

#12.1 priority

Quando duas estruturas formadas disputam o mesmo bloco:

  • a estrutura perdedora é desfeita;
  • em empate, vence o controller com o menor BlockPos.asLong();
  • o controller perdedor não forma a estrutura.

#12.2 tier

#13. Boosters (upgrades)

#13.1 O que são

Boosters são blocos colocados em células marcadas por uma única Key de upgrade no pattern. Essas células ficam fora da estrutura obrigatória e podem estar vazias:

  • não entram em members() nem em matches();
  • não afetam formed;
  • podem casar com vários boosters ao mesmo tempo;
  • cada booster tem o seu próprio limite (max_blocks);
  • o mesmo tipo de bloco pode contar para boosters diferentes.

O jogo percorre todas as células da key de upgrade e, para cada booster, conta quantas delas têm um bloco que casa com o matcher. O mesmo bloco pode contar para vários boosters, mas cada booster para no seu próprio max_blocks.

Os boosters só alteram o comportamento da máquina; a estrutura continua válida com as células de upgrade vazias.

#13.5 Validação

  • upgrades ausente: nada muda.
  • upgrades presente exige key válida e boosters não vazio.
  • key não pode ser a âncora, não pode ter matcher e precisa aparecer em pelo menos uma célula do pattern.
  • O valor do booster precisa ser finito e maior que 0; max_blocks precisa ser maior ou igual a 1.
  • modifier e mode precisam ser valores conhecidos.
  • Em mode=multiplicative com modificador de redução (speed, energy, efficiency), o valor precisa ser menor que 1.
  • output, speed, energy, efficiency e thread só têm efeito em type=recipe.
  • damage tem efeito em recipe e em storage.
  • O builder limita os modifiers por tipo e avisa quando um booster não tem efeito no type atual.
  • Um booster sem blocos correspondentes contribui com zero.
  • boosters é uma lista e, por isso, é substituída (não somada) por extends/family/overrides.

#13.6 Modificadores e matemática

Com n = min(blocos contados, max_blocks). Nas fórmulas, factor é o valor do booster (o campo output, tick_cost, energy_cost, input_cost, thread ou damage):

modeContribuição
additiveaumento: bonus += n * factor; redução: reducao += n * factor
multiplicativeaumento: fator *= (1 + factor)^n; redução: fator *= (1 - factor)^n
flatflat += n * factor (unidades absolutas)

Combinação por modificador:

Aumento (output, thread, damage):
mult = (1 + soma_additive) * produto_multiplicative
flat = soma_flat

Redução (speed, energy, efficiency):
mult = clamp((1 - soma_additive) * produto(1 - factor), 0, 1)
flat = soma_flat

Resultado por modificador:

  • output: exato = base * mult + flat; entrega max(1, floor(exato)) e usa a fração (exato - inteiro) como chance de +1. Com base maior que 0, o resultado nunca é menor que 1.
  • speed: exato = tempo_base * mult - flat; arredonda para cima, com mínimo de 1 tick.
  • energy: exato = energia_base * mult - flat; arredonda para cima, com mínimo de 1 FE por craft. O total de energia da receita não muda ao acelerar; só o custo por tick sobe.
  • efficiency: exato = input_base * mult - flat; arredonda para cima e mínimo 1.
  • thread: threads = 1 + max(0, floor((mult - 1) + flat)), limitado a 64.
  • damage: exato = dano_base * mult + flat; mínimo 0. Multiplica o dano das motions (seção 14).

Exemplo de output fracionário:

BaseMultExatoResultado
11.31.31 + 30% de +1
31.33.93 + 90% de +1
1001.3130.0130

A chance do output é rolada antes do cálculo. Se o output não couber, a parte inteira continua sendo obrigatória e o extra fracionário é ignorado (não bloqueia a receita).

#Threads: crafts paralelos

thread não reduz o tempo da receita. No fim do ciclo, o controller executa até threads crafts no mesmo tick, um após o outro, consumindo inputs e energia de cada craft. Se os inputs ou o espaço de saída acabarem antes, o loop para no craft que falhou.

  • O tempo do ciclo continua sendo o time da receita com o bônus de speed.
  • A energia total do ciclo é energia_por_craft * threads.
  • Inputs consumidos e outputs produzidos também são multiplicados pelos crafts concluídos.
  • threads fica entre 1 e 64.

#13.7 booster_button na GUI

O elemento de GUI booster_button só é aceito quando a definição tem boosters:

{ "type": "booster_button", "x": 160, "y": 4 }

  • Só é desenhado quando upgrades.boosters não está vazio.
  • Ao clicar, o cliente pede ao servidor o destaque das células de upgrade; o servidor responde e o cliente marca as células no mundo por 10s, inclusive as já ocupadas.
  • O tooltip mostra os boosters ativos e a dica de clique.

#13.8 Builder

O builder tem a etapa Boosters:

  • a Key de upgrade pode ser usada no pattern sem matcher;
  • os boosters são editados com matcher, modifier, mode, o valor do modifier e max_blocks;
  • cada booster pode ser ativado/desativado; desativados não entram no cálculo nem no JSON exportado;
  • a simulação com receita aceita um JSON importado ou colado e mostra o efeito dos boosters ativos em tempo real: tempo, energia, threads, dano das motions, quantidade dos outputs (com a chance de +1) e consumo dos inputs;
  • na simulação, cada booster ativo tem um campo de blocos, limitado por max_blocks e pela quantidade de células da key no pattern;
  • a simulação não altera a recipe do builder nem o JSON exportado;
  • o JSON exporta upgrades no nível raiz;
  • o tipo booster_button só fica disponível quando existe ao menos um booster ativo.

#13.9 Compatibilidade e reload

  • upgrades é opcional e o schema_version continua 2.
  • Definições sem upgrades funcionam como antes.
  • /reload relê a definição; o controller recalcula as células de upgrade na próxima validação da estrutura.
  • A receita ativa mantém o tempo antigo até terminar; os novos bônus valem para o próximo craft.

#14. Motions (partes móveis)

#14.1 O que são

motions permite que partes do pattern se soltem e virem uma entidade móvel:

  • em type=recipe, enquanto uma receita válida estiver rodando no controller formado;
  • em type=storage, enquanto o multibloco estiver montado.

Os blocos voltam para a posição original quando a condição deixa de valer (receita acaba ou estrutura desmonta). Cada motion escolhe quais símbolos do pattern se movem.

{

#Como a animação é amostrada

A animação é calculada a cada tick a partir do tempo decorrido:

  1. duration define o tamanho do ciclo. Com loop=true, o tempo volta para 0 ao chegar em duration; sem loop, para no último keyframe.
  2. Os keyframes precisam estar em ordem crescente de time. O jogo procura o segmento anterior -> próximo que contém o tempo atual.
  3. t é normalizado dentro do segmento (0 no keyframe anterior, 1 no próximo) e passa pelo easing do próximo keyframe; se ele não tiver easing, vale o easing global da animação.
  4. offset e rotation são interpolados linearmente com o t já suavizado.
  5. Antes do primeiro keyframe vale o primeiro; depois do último vale o último. Sem duration ou sem keyframes, a parte fica parada.

Easings:

easingFórmula
lineart
step0 até t < 1; 1 em t = 1
ease_int²
ease_out1 - (1 - t)²
ease_in_outt < 0.5: 2t²; senão 1 - (-2t + 2)² / 2

A rotação é aplicada na ordem Z, depois Y, depois X ao redor do pivot. O pivot usa o canto mínimo da parte como origem e, quando omitido, fica no centro da caixa. fill_speed multiplica a velocidade por 1 + preenchimento (de 1x a 2x) apenas em type=storage.

#14.4 Ciclo de vida

  1. O controller formado valida a estrutura normalmente.
  2. Em type=recipe, ao encontrar uma receita válida, o controller captura um snapshot de cada motion. Em type=storage, mantém as motions ativas enquanto estiver formado.
  3. O snapshot guarda posições relativas, BlockState e NBT opcional. Os blocos das keys viram ar e uma entidade multiblock_motion é criada.
  4. Enquanto houver motion ativa, as keys dessas motions são ignoradas na validação do pattern; âncora, upgrades e demais blocos continuam validando.
  5. Em type=recipe, quando não há mais receita, as entidades devolvem os blocos. Em type=storage, isso acontece ao desmontar.
  6. Se o controller for quebrado, sair do chunk ou a definição mudar, a entidade devolve os blocos e se descarta.

#14.5 Comportamento da entidade

  • Imortal, invulnerável, sem física, sem colisão e sem inventário/energia.
  • A hitbox acompanha o tamanho do snapshot.
  • Renderiza os blocos como moving blocks, com offset e rotação da animação.
  • Não aparece no preview nem no JEI.
  • Em recipe, a receita manda no ciclo; em storage, o preenchimento dos storages define apenas a velocidade quando fill_speed está ativo.
  • O dano usa o damage_source da motion; se o ID não existir no registro, usa player_attack do jogador mais próximo (16 blocos) ou generic sem jogador por perto. Selecionar minecraft:player_attack também atribui ao jogador mais próximo quando houver.

#14.6 Builder

A etapa Animações edita as motions por keys do pattern:

  • visão simples com seletor Sem animação/Custom;
  • preview 3D animado com câmera, opacidade e timeline;
  • a coluna lateral mantém a prévia da GUI; o card da prévia 3D animada é ocultado nesta etapa;
  • editor dedicado com lista de motions, preview e propriedades;
  • chips de keys com visibilidade por preview;
  • tempo da receita reescala os keyframes para o time da receita;
  • pivot manual ou automático;
  • edição de damage, damage_interval, damage_source, damage_entities e preserve_nbt;
  • damage_source usa uma única lista com os damage types vanilla mais comuns e a opção Personalizado... para digitar qualquer ID.

O preview animado também substitui a antiga prévia estática da coluna lateral nas demais etapas; o renderer estático foi removido. O preview é uma aproximação do renderer Java: usa a mesma interpolação e a mesma ordem de rotação (Z, depois Y, depois X), mas não simula luz, sombras, blockstates especiais ou entidades.

#14.7 Limitações

  • Cada símbolo do pattern pertence a no máximo uma motion.
  • fill_speed só tem efeito em type=storage.
  • Motions não aparecem no preview/JEI.
  • O nome exibido pela entidade criada ainda não é traduzível.

#15. Exportar e importar

#15.1 Exportar

No modo criativo:

  1. Segure shift.
  2. Clique com o botão direito em um controller.
  3. O JSON da estrutura conectada vai para o clipboard.
  4. A actionbar confirma e toca um som.

O scan:

  • começa no controller;
  • anda em seis direções;
  • ignora ar;
  • inclui o controller;
  • para no limite configurado em export.pattern_scan_limit (padrão 256; máximo 40960);
  • se houver mais, exporta até o limite e avisa na actionbar.

#15.2 O que o JSON exportado contém

{
  "schema_version": 2,
  "id": "infinity_nexus_multiblock:exported_0_64_0",
  "type": "storage",
  "pattern": {
    "layers": [],
    "anchor": "C",
    "matchers": {}
  }
}

Ele contém apenas:

  • schema_version;
  • id baseado nas coordenadas do controller;
  • type: "storage";
  • pattern com layers, anchor e matchers de bloco + state.

Ele não contém item_slots, capabilities, textures, model, gui, upgrades, motions, receita ou prioridade. Use como ponto de partida para o pattern.

#15.3 Normalização

A exportação normaliza posições e states para a orientação canônica SOUTH. Se você exportou uma máquina virada para norte, o JSON ainda descreve a máquina olhando para sul. Isso permite reutilizar o pattern com qualquer FACING.

#15.4 Transformar em definição

  1. Salve o JSON em data/<namespace>/multiblock/<arquivo>.json.
  2. Troque o id para <namespace>:<arquivo>.
  3. Troque type para recipe se a máquina processar receitas.
  4. Adicione item_slots, capabilities, textures, model e gui conforme necessário.
  5. Crie as receitas com type: infinity_nexus_multiblock:multiblock e definition igual ao id.
  6. Rode /reload; o controller compartilhado já existe, então não é preciso reiniciar.

Não há um exemplo exportado no repositório; use o JSON do clipboard como ponto de partida.

#15.5 Limitações da exportação

  • limite configurável em export.pattern_scan_limit (padrão 256; máximo 40960);
  • flood-fill pode incluir blocos vizinhos que não fazem parte da máquina;
  • não exporta capabilities, slots, texturas, GUI, upgrades, motions, receita ou vínculo de controller;
  • o id precisa ser ajustado;
  • o type exportado é sempre storage.

#16. Reload e ciclo de vida

Use /reload no servidor.

O que acontece:

  • as definições são recarregadas e revalidadas;
  • controllers formados usam a definição mais recente do mesmo id;
  • se a definição não existir mais, a estrutura é invalidada;
  • inventário e layout da GUI são reconfigurados quando a definição muda;
  • stacks que não cabem no novo inventário são descartados;
  • capabilities de energia/fluidos já existentes não são recriadas nem reconfiguradas;
  • capabilities ausentes podem ser criadas quando a definição fica disponível;
  • as definições resolvidas são enviadas aos clientes para a preview;
  • receitas de controller são regeneradas a partir do jar do mod e de kubejs/data;
  • o layout da GUI é persistido no block entity para sobreviver ao carregamento.

Se você mudou capacity, max_receive, max_extract ou filter de uma capability existente, quebre e coloque o controller de novo, ou reinicie o mundo.

Para adicionar ou remover uma definição, basta /reload; o bloco controller é compartilhado e já está registrado.

#20. Limitações atuais

#20.1 Controller único

  • Existe um único bloco/item controller: infinity_nexus_multiblock:multiblock_controller.
  • O vínculo com a máquina vem do componente infinity_nexus_multiblock:multiblock_definition; não há bloco ou item por definição, mas o modelo do controller pode ser especializado com textures e model.
  • A aba criativa mostra uma variante do controller para cada definição carregada.
  • /reload atualiza definições e receitas; não é necessário reiniciar para adicionar, remover ou sobrescrever uma definição.
  • O antigo bloco nexus_core e os controllers dinâmicos foram removidos. Mundos antigos podem gerar avisos de registry; faça backup antes de atualizar.

#20.2 Máquinas, receitas e automação

  • Toda receita de máquina usa type: infinity_nexus_multiblock:multiblock e definition: <id>. Não há tipo independente por máquina.
  • type=storage já funciona como inventário/capabilities/GUI e aceita motions; não há regras dedicadas de armazenamento. tier é apenas metadado.
  • Receitas usam inputs/outputs tipados: item, fluido, entidade, energia e recursos de addon, com múltiplas saídas e chance por output.
  • Não há prioridade entre receitas; a primeira receita compatível encontrada é usada.
  • Energia e fluidos não têm configuração por lado; as capabilities do controller e dos membros selecionados aceitam todas as faces. capability_ports escolhe blocos, não faces.
  • As faces de item_slots são direções do mundo e não giram com o controller/estrutura.
  • Matchers aceitam bloco, tag e state; não aceitam NBT, listas de alternativas ou matchers opcionais.

#20.3 Assets, JEI e reload

  • O controller compartilhado tem blockstate, modelo base, loot e traduções próprios; texturas e modelos por definição vêm de textures e model e são aplicados em runtime.
  • O nome exibido usa multiblock.<namespace>.<path> e cai no path formatado quando não há tradução.
  • A categoria JEI de receitas é filtrada pela definição do controller.
  • A categoria JEI de estruturas ainda usa um catalisador genérico e pode listar todas as estruturas; o filtro por definição é uma melhoria pendente.
  • A transferência JEI de itens existe, mas ainda não foi validada visualmente no cliente; fluidos continuam manuais.
  • /reload recarrega definições, receitas de controller e o pack de dados; não recria capabilities já existentes.

#20.4 Exportação

  • A exportação é limitada por export.pattern_scan_limit na config comum do mod (config/infinity_nexus_multiblock-common.toml): padrão 256, máximo 40960.
  • O JSON exportado contém apenas schema_version, id, type e pattern (blocos e states); não inclui item_slots, capabilities, textures, gui, upgrades, motions, receita ou prioridade, e o type exportado é sempre storage.

#20.5 Metas ainda não atendidas

  • Comportamento especializado de type=storage além do básico já implementado (inventário, capabilities, GUI, motions e booster de dano).
  • Filtro da categoria JEI de estruturas por definição e validação visual da transferência JEI.
  • Adaptadores para receitas vanilla.
  • Nome traduzível para a entidade multiblock_motion.
